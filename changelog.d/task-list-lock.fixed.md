- `GET /api/tasks`, `GET /api/tasks/registry`, the task-group lookups and `GET /api/graphs` no longer filter, sort or count while holding the store lock, so a long scan no longer makes event ingestion wait. The task lists copy the per-task records under the lock (a reference copy that grows in proportion to the number of tasks) and filter outside it. The graph list reads a snapshot of the flow order and times that the server publishes when it computes them, plus the few roots that came or went since, so its hold does not grow with the number of flows. Measured at 100,000 one-task tasks or flows, as the best and the median of 9 alternating runs on a 2-vCPU host, the summed lock hold per call went from 151 and 159 ms to 2.9 and 3.2 ms for the default task list, from 253 and 259 ms to 2.9 and 3.1 ms for the `hostname` filter, from 200 and 204 ms to 2.3 and 2.8 ms for `sort`, from 107 and 110 ms to 2.5 and 2.7 ms for the task registry's run summaries, from 18 and 19 ms to 0.25 and 0.28 ms for the unfiltered graph list, and from 90 and 99 ms to 0.61 and 0.64 ms for the graph list with `from_date`.
- The graph list filtered by task name, the first flow-time computation after a change, and eviction still hold the lock for the whole store.
- A task list row that changes while the list is built stays on the page with its current values, even if they no longer match the filter or the `sort`; `sort` used to drop such a row. A row whose task was evicted in that time, even if the ID came back, is left out, and `total` counts the matches when the filter ran.
