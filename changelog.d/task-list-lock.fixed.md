- `GET /api/tasks`, the graph list with `from_date` or `to_date`, `GET /api/tasks/registry` and the task-group lookups no longer make event ingestion wait while they filter. They copy the per-task records under the store lock and filter, sort and count outside it, so the lock hold no longer grows with the number of stored tasks. On a 20,000-task store with a list scanning nonstop, the 99th percentile wait of `add_event` for the `hostname`, `queue` and `exception_type` filters and the default list was 160, 152, 86 and 66 ms before and 3.3, 4.8, 3.7 and 1.5 ms after (`tests/unit/test_store_bounded_reads.py`). The graph list filtered by task name and the first flow-time computation after a change still hold the lock for the whole store, as does eviction.
- A task list row that changes while the list is built now stays on the page with its newest state, even if it no longer matches the filter or the sort that was asked for. This includes the `sort` parameter, which used to drop the row. A row evicted in that time is still left out, and `total` counts the matches when the filter ran.
